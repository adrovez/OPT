1. Resumen Ejecutivo

BUENO

El frontend presenta una arquitectura bien fundada: capas separadas, modelos centralizados, lazy loading completo y patrones Angular modernos. No obstante, acumula deuda técnica media concentrada en tres áreas: acoplamiento a localStorage, ausencia de interfaces para servicios, y componentes con responsabilidades múltiples. La deuda es corregible en 1–2 sprints sin riesgo de regresión estructural.

5. Hallazgos Detallados

✅ Fortalezas Identificadas

Servicios de catálogo con shareReplay(1)
region.service.ts:17–19 · prevision.service.ts:15
ISP Performance
Los catálogos compartidos (regiones, previsiones, roles, formas de pago) usan shareReplay(1), evitando peticiones HTTP duplicadas. Patrón consistente en todos los servicios de catálogo. 
private readonly regiones$ = this.http
  .get<RegionWithComunas[]>(`${this.apiUrl}/WithComunas`)
  .pipe(shareReplay(1));  ✓
takeUntilDestroyed en 90% de suscripciones
cliente-form.component.ts:485 · stock-list.component.ts:909
Memory Safety Angular 16+
La mayoría de suscripciones a Observables están correctamente protegidas con takeUntilDestroyed(this.destroyRef), previniendo memory leaks en navegación entre vistas.
Lazy loading en todas las rutas
app.routes.ts:12–14, 22–26
Performance Clean Arch
Todas las rutas de negocio usan loadComponent(). El bundle inicial es mínimo y cada módulo se carga bajo demanda, cumpliendo al 100% con la separación por features.
Multi-tenancy correctamente encapsulado
atencion.service.ts:14–16 · agenda.service.ts:14–16
SRP Encapsulación
El header X-Sucursal-Id se resuelve automáticamente en cada servicio via SucursalContextService. Los componentes no conocen el header y no tienen que gestionarlo. 
private headers(): HttpHeaders {
  const sucursalId = this.sucursalContext.sucursalActual()?.sucursalId ?? '';
  return new HttpHeaders({ 'X-Sucursal-Id': sucursalId });
}  ✓

❌ Problemas Encontrados

P-01 · DIP violado — localStorage acoplado directamente
auth.service.ts:23,36,46 · sucursal-context.service.ts:14,23,29 · auth.interceptor.ts:4
DIP Alta
Tres archivos de capa core acceden directamente a localStorage, creando acoplamiento a una implementación de infraestructura del navegador. Imposible testear unitariamente sin mock de DOM, e imposible migrar a sessionStorage o IndexedDB sin refactor. 
// ❌ auth.service.ts — dependencia concreta
localStorage.setItem(TOKEN_KEY, response.token);
const user = localStorage.getItem(USER_KEY);

// ❌ auth.interceptor.ts — duplicación del acoplamiento
const token = localStorage.getItem('opt_token');

// ✓ Solución: crear StorageService abstracto
@Injectable({ providedIn: 'root' })
export class StorageService {
  get(key: string): string | null { return localStorage.getItem(key); }
  set(key: string, value: string): void { localStorage.setItem(key, value); }
  remove(key: string): void { localStorage.removeItem(key); }
}
P-02 · OCP/DIP — Servicios sin interfaces (no testeables)
core/services/*.service.ts (todos)
DIP OCP Media
Ningún servicio del proyecto implementa una interfaz TypeScript formal. Los componentes dependen de clases concretas, haciendo imposible el testeo con dobles de prueba sin configuración compleja de Angular TestBed. 
// ❌ Actual — dependencia concreta
constructor(private clienteService: ClienteService) {}

// ✓ Ideal — dependencia de abstracción
export abstract class ClienteService {
  abstract getClientes(params: ClienteFilter): Observable<PagedResult<Cliente>>;
  abstract getCliente(id: string): Observable<Cliente>;
  // ...
}

P-04 · Memory leak — suscripciones sin takeUntilDestroyed
clientes-list.component.ts:289,337 · productos-list.component.ts:481,497
Memory Leak Alta
Varias suscripciones en métodos de carga (cargarClientes(), cargarCategorias()) no usan takeUntilDestroyed. En apps con navegación frecuente esto acumula suscripciones activas que nunca se cancelan. 
// ❌ clientes-list.component.ts:289
this.clienteService.getClientes(...).subscribe({
  next: (response) => { ... },
});

// ✓ Corrección
this.clienteService.getClientes(...)
  .pipe(takeUntilDestroyed(this.destroyRef))
  .subscribe({ next: (response) => { ... } });
P-05 · Inconsistencia — Mezcla de Signal Forms y ReactiveFormsModule
cliente-form.component.ts · usuario-form.component.ts
Inconsistencia Baja-Media
El proyecto declara Signal Forms como estándar en CLAUDE.md, pero cliente-form.component.ts y usuario-form.component.ts usan ReactiveFormsModule con FormBuilder. Deuda técnica reconocida para usuario-form, pero no para cliente-form.
P-06 · SRP leve — Lógica de formato de fechas duplicada en componentes
atenciones-list.component.ts:17–28 · stock-list.component.ts:1170–1207
SRP Baja
Funciones de formato de fechas y helpers de presentación están definidas directamente en los archivos de componentes. Si el mismo formato es necesario en otro módulo, hay que duplicar. Solucionable con un Angular Pipe o un DateFormatService. 
// ❌ Duplicado en atenciones-list.component.ts
function pad(n: number): string { return String(n).padStart(2, '0'); }
function formatFecha(iso: string): string { ... }
function formatHora(iso: string): string { ... }

// ✓ Extraer a pipe reutilizable
@Pipe({ name: 'optFecha', standalone: true })
export class OptFechaPipe implements PipeTransform { ... }

7. Roadmap de Mejoras Recomendado

1

Crear StorageService — eliminar acoplamiento a localStorage

Extraer todos los accesos a localStorage en auth.service.ts, sucursal-context.service.ts y auth.interceptor.ts hacia un servicio StorageService inyectable. Habilita mocks en tests y posible migración futura.

Esfuerzo: ~2h · Impacto: Alto (DIP + testabilidad)
2

Completar takeUntilDestroyed en todas las suscripciones

Buscar todos los .subscribe({ sin pipe precedente en clientes-list.component.ts y productos-list.component.ts. Agregar .pipe(takeUntilDestroyed(this.destroyRef)) en cada caso.

Esfuerzo: ~1h · Impacto: Alto (memory leaks)
3

Migrar cliente-form a Signal Forms

Reemplazar FormBuilder + ReactiveFormsModule por Signal Forms en cliente-form.component.ts. Aprovechar la migración para extraer la lógica de contactos a un sub-componente ContactoFormComponent.

Esfuerzo: ~4h · Impacto: Medio (consistencia + SRP)
4

Dividir StockListComponent en sub-componentes por tab

Extraer StockActualTabComponent, EntradasTabComponent, HistorialTabComponent y TransferenciasTabComponent. El componente host pasa solo datos y eventos via @Input/@Output.

Esfuerzo: ~6h · Impacto: Medio (mantenibilidad + SRP)
5

Agregar interfaces abstractas para los servicios principales

Definir abstract class ClienteService, AtencionService, StockService y ProductoService con los métodos públicos. Las implementaciones concretas los extienden. Permite crear doubles de prueba sin HttpClientTestingModule.

Esfuerzo: ~3h · Impacto: Medio (OCP + DIP + testabilidad)
6

Crear OptFechaPipe — centralizar formateo de fechas

Extraer las funciones formatFecha(), formatHora() y pad() dispersas en componentes a un Angular Pipe standalone reutilizable. Registrar en core/pipes/.

Esfuerzo: ~1h · Impacto: Bajo (DRY + SRP)
