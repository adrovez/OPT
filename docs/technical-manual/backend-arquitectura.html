Manual de Arquitectura Backend

OPT SaaS · .NET 10 · Clean Architecture · Multi-Tenant · JWT

Visión General

OPT es un SaaS multi-tenant para gestión de ópticas. El backend está implementado en .NET 10 siguiendo Clean Architecture con cuatro capas bien definidas. La seguridad multi-tenant es el principio rector de toda decisión de diseño.

Regla de oro: Ningún endpoint puede exponer ni modificar datos de un tenant diferente al del usuario autenticado, bajo ninguna circunstancia.

🔷 Domain

Entidades puras, sin dependencias externas. La fuente de verdad del modelo.

🔵 Application

Casos de uso (CQRS con MediatR). Solo conoce abstracciones, nunca clases concretas de infraestructura.

🟢 Infrastructure

EF Core, SQL Server, JWT, BCrypt. Implementa los contratos de Application.

🟡 API

Controllers delgados, Middleware, DI wiring. Orquesta sin lógica de negocio.

Middleware Personalizados

1. CorrelationIdMiddleware

Genera o reutiliza el header X-Correlation-Id de cada request. Lo inyecta en el scope del logger para que todos los logs del request (en cualquier capa) compartan el mismo ID. Esencial para rastrear errores en producción multi-tenant.

// El cliente puede enviar: X-Correlation-Id: mi-id-personalizado
// Si no lo envía, se genera: X-Correlation-Id: a3f2b1c0d4e5f6a7...
// Aparece en la respuesta y en todos los logs del request

2. ExceptionHandlingMiddleware

Captura TODAS las excepciones no controladas. Las convierte en respuestas RFC 7807 ProblemDetails. Los controllers no necesitan try/catch.

Excepción lanzadaHTTPCuándo usarla
ValidationException400FluentValidation falla en el command
UnauthorizedAccessException401Credenciales incorrectas en login
KeyNotFoundException404Entidad no encontrada o de otro tenant
InvalidOperationException409Regla de negocio violada (ej. RUT duplicado)
Exception (resto)500Error inesperado — detalle NO expuesto al cliente
// Ejemplo de respuesta 409 ProblemDetails:
{
  "status": 409,
  "title": "Operación inválida",
  "detail": "Ya existe un cliente con el documento '12345678-9' en este tenant.",
  "instance": "/api/cliente"
}

3. TenantValidationMiddleware

Segunda línea de defensa multi-tenant. Se ejecuta después de UseAuthorization(), cuando los claims del JWT ya están disponibles. Valida que tenant_id sea un entero mayor a 0.

¿Por qué es necesario si JWT ya valida la firma? JwtBearer verifica la firma criptográfica pero no el contenido semántico. Un token firmado con tenant_id: 0 o sin el claim pasaría la verificación. Este middleware rechaza esos casos con 403 Forbidden.

Seguridad Multi-Tenant

Reglas no negociables: Todos los repositorios deben filtrar por TenantId explícitamente en cada consulta. Los query filters globales de EF son la segunda línea, no la primera.

Tres capas de protección

CapaMecanismoResponsabilidad
1. MiddlewareTenantValidationMiddlewareRechaza tokens sin tenant_id válido antes de llegar a controllers
2. RepositoriosParámetro TenantId explícitoCada query incluye WHERE TenantId = @tenantId
3. OPTDbContextHasQueryFilter(e => !e.IsDeleted)Excluye automáticamente registros con soft-delete

Soft-Delete obligatorio

Nunca usar DELETE físico. Siempre marcar IsDeleted = true. El QueryFilter de EF excluye estos registros automáticamente en todas las consultas.

// ✅ Correcto — soft delete
cliente.IsDeleted = true;
cliente.UpdatedAt = DateTime.UtcNow;
await context.SaveChangesAsync();

// ❌ Incorrecto — delete físico
context.Clientes.Remove(cliente);

JWT y Claims

El token JWT incluye estos claims en cada autenticación exitosa:

{
  "sub":         "1",             // UsuarioId
  "tenant_id":   "1",             // TenantId — claim personalizado
  "rut_usuario": "12345678-9",    // RUT del usuario
  "name":        "Juan Pérez",    // Nombre completo
  "role":        "Operador",      // Rol: Admin | Operador | Lectura
  "jti":         "guid-único",    // JWT ID para prevenir replay
  "exp":         1746500000       // Expiración Unix timestamp
}

Configuración en appsettings.json

{
  "Jwt": {
    "Secret":            "OPT-SecretKey-ChangeThis-InProduction-2026-SecureKey!",
    "Issuer":            "OPT",
    "Audience":          "OPT",
    "ExpirationMinutes": 60
  }
}
Producción: El Secret debe ser una cadena de al menos 32 caracteres aleatorios, almacenada en variables de entorno o Azure Key Vault, nunca en el repositorio.

Guía: Agregar un Nuevo Módulo

Ejemplo de referencia: módulo Sucursal (ya implementado en Sesión 11). Usar como patrón para el siguiente módulo.

Paso 1 — Domain

// OPT.Domain/Entities/NuevoModulo.cs
public class NuevoModulo {
    public Guid NuevoModuloId { get; set; }  // UNIQUEIDENTIFIER (NEWSEQUENTIALID())
    public Guid TenantId { get; set; }       // FK → OPT_Tenant
    public string Nombre { get; set; } = string.Empty;
    // ... campos específicos
    // Auditoría: CreatedAt, UpdatedAt, CreatedBy, UpdatedBy, IsDeleted
}

Paso 2 — Application: Interface + Commands + Queries + Validators

// OPT.Application/Interfaces/INuevoModuloRepository.cs
public interface INuevoModuloRepository {
    Task<IReadOnlyList<NuevoModulo>> GetAllAsync(Guid tenantId);
    Task<NuevoModulo?> GetByIdAsync(Guid id, Guid tenantId);
    Task AddAsync(NuevoModulo entity);
    Task UpdateAsync(NuevoModulo entity);
    Task SoftDeleteAsync(Guid id, Guid tenantId, string deletedBy);
}

Paso 3 — Infrastructure: Repository + DbContext

// En OPTDbContext.OnModelCreating:
modelBuilder.Entity<NuevoModulo>(e => {
    e.ToTable("OPT_NuevoModulo");
    e.HasKey(x => x.NuevoModuloId);
    e.Property(x => x.NuevoModuloId).HasDefaultValueSql("NEWSEQUENTIALID()");
    e.HasIndex(x => x.TenantId).HasFilter("[IsDeleted] = 0");
    e.HasQueryFilter(x => !x.IsDeleted);
});

Paso 4 — API: Controller delgado (sin try/catch)

[ApiController]
[Route("api/nuevomodulo")]
[Authorize]
public class NuevoModuloController(IMediator mediator, ICurrentTenantService tenantService)
    : ControllerBase {
    [HttpGet]
    public async Task<IActionResult> GetAll(CancellationToken ct) {
        var result = await mediator.Send(new GetNuevoModuloQuery(tenantService.TenantId), ct);
        return Ok(result);
    }
    // ... GetById, Create (201), Update (204), Delete (204)
}

Paso 5 — Script SQL (si hay nuevas tablas)

-- src/basedatos/012_OPT_NuevoModulo.sql
-- Próximo número secuencial disponible: 012
CREATE TABLE [dbo].[OPT_NuevoModulo] (
    [NuevoModuloId] UNIQUEIDENTIFIER NOT NULL DEFAULT NEWSEQUENTIALID(),
    [TenantId]      UNIQUEIDENTIFIER NOT NULL,
    -- ... campos
    [IsDeleted]     BIT NOT NULL DEFAULT 0,
    CONSTRAINT [PK_OPT_NuevoModulo] PRIMARY KEY CLUSTERED ([NuevoModuloId])
);

Anti-patrones a Evitar

❌ Anti-patrón✅ Alternativa correcta
Lógica de negocio en ControllerMover al Command/Query handler en Application
Acceder a OPTDbContext desde ApplicationUsar la interface de repositorio correspondiente
Hardcodear TenantId en queriesSiempre extraer de ICurrentTenantService
DELETE físico en tabla de negocioSoft-delete: IsDeleted = true
try/catch en controllersLanzar excepción semántica; el middleware la maneja
Lanzar Exception genérica desde handlerUsar la excepción correcta: KeyNotFoundException, InvalidOperationException, etc.
Loguear PasswordHash o tokens JWTLoguear solo IDs, timestamps y mensajes de error
Saltar capas (API → Infrastructure directo)Respetar el flujo: API → Application → Infrastructure
