Manual de Arquitectura Backend

OPT SaaS · .NET 10 · Clean Architecture · Multi-Tenant · JWT

Visión General

OPT es un SaaS multi-tenant para gestión de ópticas. El backend está implementado en .NET 10 siguiendo Clean Architecture con cuatro capas bien definidas. La seguridad multi-tenant es el principio rector de toda decisión de diseño.

Regla de oro: Ningún endpoint puede exponer ni modificar datos de un tenant diferente al del usuario autenticado, bajo ninguna circunstancia.

🔷 Domain

Entidades puras, sin dependencias externas. La fuente de verdad del modelo.

🔵 Application

Casos de uso (CQRS con MediatR). Solo conoce abstracciones, nunca clases concretas de infraestructura.

🟢 Infrastructure

EF Core, SQL Server, JWT, BCrypt. Implementa los contratos de Application.

🟡 API

Controllers delgados, Middleware, DI wiring. Orquesta sin lógica de negocio.

Middleware Personalizados

1. CorrelationIdMiddleware

Genera o reutiliza el header X-Correlation-Id de cada request. Lo inyecta en el scope del logger para que todos los logs del request (en cualquier capa) compartan el mismo ID. Esencial para rastrear errores en producción multi-tenant.

// El cliente puede enviar: X-Correlation-Id: mi-id-personalizado
// Si no lo envía, se genera: X-Correlation-Id: a3f2b1c0d4e5f6a7...
// Aparece en la respuesta y en todos los logs del request

2. ExceptionHandlingMiddleware

Captura TODAS las excepciones no controladas. Las convierte en respuestas RFC 7807 ProblemDetails. Los controllers no necesitan try/catch.

Excepción lanzadaHTTPCuándo usarla
ValidationException400FluentValidation falla en el command
UnauthorizedAccessException401Credenciales incorrectas en login
KeyNotFoundException404Entidad no encontrada o de otro tenant
InvalidOperationException409Regla de negocio violada (ej. RUT duplicado)
Exception (resto)500Error inesperado — detalle NO expuesto al cliente
// Ejemplo de respuesta 409 ProblemDetails:
{
  "status": 409,
  "title": "Operación inválida",
  "detail": "Ya existe un cliente con el documento '12345678-9' en este tenant.",
  "instance": "/api/cliente"
}

3. TenantValidationMiddleware

Segunda línea de defensa multi-tenant. Se ejecuta después de UseAuthorization(), cuando los claims del JWT ya están disponibles. Valida que tenant_id sea un entero mayor a 0.

¿Por qué es necesario si JWT ya valida la firma? JwtBearer verifica la firma criptográfica pero no el contenido semántico. Un token firmado con tenant_id: 0 o sin el claim pasaría la verificación. Este middleware rechaza esos casos con 403 Forbidden.

Seguridad Multi-Tenant

Reglas no negociables: Todos los repositorios deben filtrar por TenantId explícitamente en cada consulta. Los query filters globales de EF son la segunda línea, no la primera.

Tres capas de protección

CapaMecanismoResponsabilidad
1. MiddlewareTenantValidationMiddlewareRechaza tokens sin tenant_id válido antes de llegar a controllers
2. RepositoriosParámetro TenantId explícitoCada query incluye WHERE TenantId = @tenantId
3. OPTDbContextHasQueryFilter(e => !e.IsDeleted)Excluye automáticamente registros con soft-delete

Soft-Delete obligatorio

Nunca usar DELETE físico. Siempre marcar IsDeleted = true. El QueryFilter de EF excluye estos registros automáticamente en todas las consultas.

// ✅ Correcto — soft delete
cliente.IsDeleted = true;
cliente.UpdatedAt = DateTime.UtcNow;
await context.SaveChangesAsync();

// ❌ Incorrecto — delete físico
context.Clientes.Remove(cliente);

JWT y Claims

El token JWT incluye estos claims en cada autenticación exitosa:

{
  "sub":         "1",             // UsuarioId
  "tenant_id":   "1",             // TenantId — claim personalizado
  "rut_usuario": "12345678-9",    // RUT del usuario
  "name":        "Juan Pérez",    // Nombre completo
  "role":        "Operador",      // Rol: Admin | Operador | Lectura
  "jti":         "guid-único",    // JWT ID para prevenir replay
  "exp":         1746500000       // Expiración Unix timestamp
}

Configuración en appsettings.json

{
  "Jwt": {
    "Secret":            "",
    "Issuer":            "OPT",
    "Audience":          "OPT",
    "ExpirationMinutes": 60
  }
}
JWT Secret obligatorio en entorno: Secret está vacío en el repositorio. El startup lanza InvalidOperationException si no se configura con al menos 32 caracteres. Usar dotnet user-secrets en desarrollo o variable de entorno Jwt__Secret en producción. Ver sección Seguridad para instrucciones detalladas.

// En OPTDbContext.OnModelCreating:

Regla crítica — ICurrentTenantService: Solo se usa en controllers y middleware. Los handlers de Application NO inyectan ICurrentTenantService. El controller extrae TenantId/SucursalId/UsuarioId/CreatedBy y los pasa en el command/query. Inyectarlo en handlers viola Clean Architecture.
Módulos frontend pendientes: Salida por documentos (Devoluciones, OtroEgreso — solo Salida directa disponible), Dashboard/Home screen, Autorización por rol en controllers.

Seguridad

Mecanismos de seguridad implementados en el backend. Todos los cambios se aplicaron en la sesión 29 (2026-06-08) como parte de una auditoría formal.

JWT Secret — Configuración obligatoria

appsettings.json tiene "Secret": "". El startup lanza InvalidOperationException si el secret está vacío o tiene menos de 32 caracteres. Nunca commitear el valor real al repositorio.

# Desarrollo — User Secrets
dotnet user-secrets set "Jwt:Secret" "min-32-chars-random-value"

# Producción — variable de entorno (doble underscore = sección)
Jwt__Secret=min-32-chars-random-value

Adicionalmente, ClockSkew = TimeSpan.Zero en TokenValidationParameters para que los tokens expiren exactamente al tiempo configurado sin los 5 minutos de gracia por defecto.

Refresh Token — Arquitectura

El sistema de autenticación emite dos tokens en cada login: un access token (JWT, duración configurable via ExpirationMinutes) y un refresh token (opaco, 7 días).

EndpointAuthDescripción
POST /api/Auth/loginNoDevuelve par {token, refreshToken}. Rate limited: 5 req/min → 429.
POST /api/Auth/refreshNo (refresh token autentica)Rota el par completo. El token anterior queda revocado (one-use).
POST /api/Auth/logoutJWT requeridoRevoca el refresh token en BD. TenantId del JWT, no del body.

Almacenamiento seguro: el valor raw del refresh token nunca persiste en base de datos. Se guarda únicamente el hash SHA-256 en hexadecimal (64 chars) en la columna TokenHash de OPT_RefreshToken. Esto evita que una brecha en la BD permita robar tokens activos.

Rotación one-use: cada llamada a /refresh revoca el token anterior y emite un par nuevo. Si el mismo token se usa dos veces, la segunda llamada falla con 401.

Validación cross-tenant: RefreshTokenCommandHandler verifica que storedToken.TenantId == request.TenantId antes de rotar. El logout extrae el TenantId del JWT autenticado.

En el frontend, auth.interceptor.ts intercepta respuestas 401 (excepto las de /Auth/login y /Auth/refresh), llama automáticamente a /refresh, y reintenta la request original con el nuevo token. Si el refresh también falla, ejecuta logout local.

Rate Limiting en Login

Configurado con el middleware nativo de .NET 8+ (Microsoft.AspNetCore.RateLimiting). Política "login": ventana fija de 1 minuto, 5 requests máximos por IP. Retorna 429 Too Many Requests al superar el límite.

// Program.cs
builder.Services.AddRateLimiter(opts => {
    opts.AddFixedWindowLimiter("login", o => {
        o.PermitLimit = 5;
        o.Window = TimeSpan.FromMinutes(1);
    });
    opts.RejectionStatusCode = 429;
});

// AuthController
[HttpPost("login")]
[EnableRateLimiting("login")]
public async Task<IActionResult> Login(...)

ChangePassword — Control de acceso

PUT /api/usuarios/{id}/password verifica que el llamante sea el propietario de la cuenta o tenga rol Admin. De lo contrario retorna 403 Forbidden.

if (id != tenantService.UsuarioId && !User.IsInRole("Admin"))
    return Forbid();

RBAC — Estado actual (deuda técnica)

El claim role (Admin | Operador | Lectura) está presente en el JWT pero solo se verifica en endpoints puntuales. Todos los endpoints de escritura tienen [Authorize] (cualquier rol autenticado). La aplicación de roles granulares es una deuda técnica pendiente:

RolAcceso actualAcceso objetivo
AdminTodoTodo
OperadorTodo (no diferenciado)Mutations clínicas/financieras; no gestión de usuarios/sucursales
LecturaTodo (no diferenciado)Solo GET endpoints
