1. Vista General del Sistema

OPT es una plataforma SaaS multi-tenant para la gestion de opticas. El sistema permite que multiples opticas (tenants) operen de forma aislada, compartiendo la misma infraestructura pero con datos completamente separados.

Principio rector: Ningun endpoint puede exponer datos cross-tenant por error de codigo. La seguridad multi-tenant es la prioridad maxima.

5. API: Tenant

Publico — No requiere autenticacion. Gestion de tenants del SaaS.

GET /api/tenants

Listar todos los tenants (sin soft-deleted).

Response: 200 OK — Array de TenantDto

GET /api/tenants/{id}

Obtener tenant por ID.

Response: 200 OK / 404 Not Found

POST /api/tenants

Crear nuevo tenant.

Body:

{
  "nombre": "Optica Central S.A.",
  "rutEmpresa": "76123456-7",
  "direccion": "Av. Libertador 1234, Santiago",
  "email": "contacto@opticacentral.cl",
  "telefono": "+56 2 2345 6789"
}

Response: 201 Created con TenantDto

PUT /api/tenants/{id}

Actualizar tenant existente.

Body:

{
  "nombre": "Optica Central S.A. (Actualizado)",
  "direccion": "Nueva Direccion 567",
  "email": "nuevo@opticacentral.cl",
  "telefono": "+56 9 1234 5678",
  "activo": true
}

Response: 200 OK con TenantDto

DELETE /api/tenants/{id}

Soft-delete de tenant (IsDeleted = true).

Response: 204 No Content

7. API: Clientes

Requiere JWT — Todos los endpoints extraen TenantId del token JWT automaticamente.

GET /api/clientes?page=1&pageSize=20&search=

Listado paginado de clientes del tenant autenticado. Busqueda por nombre, documento o email.

Response: PagedResult<ClienteDto>

GET /api/clientes/{id}

Obtener cliente por ID (valida que pertenezca al tenant).

Response: 200 OK / 404

POST /api/clientes

Crear cliente. El TenantId se inyecta desde el JWT (no se acepta del body).

Body (Persona):

{
  "tipoCliente": "Persona",
  "numeroDocumento": "12345678-9",
  "nombre": "Juan Perez",
  "direccion": "Calle 123, Santiago",
  "idComuna": 7,
  "celular": "+56 9 1234 5678",
  "mail": "juan@email.com",
  "fechaNacimiento": "1990-05-15",
  "tipoPrevision": "Fonasa",
  "giro": null
}

Body (Empresa):

{
  "tipoCliente": "Empresa",
  "numeroDocumento": "76123456-7",
  "nombre": "Empresa ABC SpA",
  "direccion": "Av. Industrial 456",
  "idComuna": 5,
  "celular": "+56 2 2345 6789",
  "mail": "contacto@empresaabc.cl",
  "fechaNacimiento": null,
  "tipoPrevision": null,
  "giro": "Comercio al por mayor"

Response: 201 Created con ClienteDto

PUT /api/clientes/{id}

Actualizar cliente (valida tenant + unicidad de documento).

Response: 200 OK / 404 / 400

Soft-delete de cliente.

Response: 204 No Content

10. Patrones de Diseno

CQRS con MediatR (Vertical Slices)

Cada caso de uso se implementa como un comando o query independiente con su propio handler:

// Command
public record CreateTenantCommand(CreateTenantDto Dto)
    : IRequest<Result<TenantDto>>;

// Handler
public class CreateTenantHandler(ITenantRepository repository)
    : IRequestHandler<CreateTenantCommand, Result<TenantDto>>
{
    public async Task<Result<TenantDto>> Handle(
        CreateTenantCommand request, CancellationToken ct)
    {
        // Validaciones, logica de negocio, persistencia
        return Result<TenantDto>.Success(dto);
    }
}

Result Pattern

// Exitoso
return Result<T>.Success(data);

// Error
return Result<T>.Failure("Mensaje de error");

DTOs como Records Inmutables

public record TenantDto(

    string Nombre,
    string RutEmpresa,
    string? Direccion,
    string Email,

public class CreateTenantValidator : AbstractValidator<CreateTenantCommand>

  1. Ejecutar scripts SQL en orden (src/basedatos/000_ hasta 008_)

    "ConnectionStrings": {
  "DefaultConnection": "Server=localhost;Database=dbOPT;Trusted_Connection=True;TrustServerCertificate=True;"
}
  3. Configurar JWT secret en appsettings.json: 
    "Jwt": {
  "Secret": "TU-SECRET-KEY-MUY-LARGO-Y-SEGURO-2026!",
  "Issuer": "OPT",
  "Audience": "OPT",
  "ExpirationMinutes": 60

  4. Restaurar paquetes: dotnet restore
  5. Compilar: dotnet build

12. Seguridad Multi-Tenant

Como funciona el aislamiento

  1. Autenticacion: El usuario se loguea con RUT + password + TenantId
  2. Token JWT: Contiene TenantId como claim
  3. En cada request: El controller extrae TenantId del JWT claim
  4. En cada query: El repositorio filtra por TenantId automaticamente
  5. EF Core Query Filters: HasQueryFilter(e => !e.IsDeleted) en AppDbContext

Reglas de seguridad

ReglaImplementacion
Datos aislados por tenantTenantId en todas las queries de negocio
Soft-delete globalQuery filter en AppDbContext
Unicidad de documentoIndex unico: (TenantId, NumeroDocumento) where IsDeleted = 0
Passwords segurosBCrypt hashing (nunca texto plano)
Tokens con expiracionJWT con Expires configurable (default 60 min)

Importante: Los controllers de Clientes y Contactos tienen el atributo [Authorize]. El TenantId nunca se acepta del request body para operaciones autenticadas — siempre se extrae del JWT claim.

13. Migracion desde Legacy

Legacy vs Nuevo

AspectoLegacy (old/)Nuevo (src/backend/)
Framework.NET Framework + ASP.NET MVC.NET 10 + Minimal API / Controllers
ORMEntity Framework 6 (Database First)EF Core 9.0 (Code First)
AuthForms Authentication + SessionJWT Bearer + BCrypt
ArquitecturaWeb + Dato + Entidad (3 capas)Clean Architecture (4 capas)
Multi-tenantNo existia (single tenant)SaaS con TenantId en todo
Persona/Empresa2 tablas separadas1 tabla unificada con TipoCliente
Soft-deleteNo implementadoIsDeleted en todas las tablas

Decisiones de migracion clave

  • Cliente unificado: Se elimino la tabla OPT_Empresa. Ahora Persona y Empresa comparten OPT_Cliente con TipoCliente.
  • NumeroDocumento: Reemplazo a RutCliente del legacy. Soporta RUT de persona y RUT de empresa.
  • Usuario: Nueva tabla con PasswordHash (BCrypt). El legacy guardaba passwords en texto plano.
  • Multi-tenant: Se agrego TenantId a todas las tablas de negocio como requisito del nuevo modelo SaaS.
